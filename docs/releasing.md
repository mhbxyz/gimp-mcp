# Releasing

Releases are reproducible: the same commit always gives byte-identical
artifacts (`tests/unit/test_distribution.py::test_builds_are_reproducible`).
Design and verified facts: [ADR 0002](adr/0002-release-pipeline.md).

## Cutting a release

1. Make sure `## [Unreleased]` in `CHANGELOG.md` lists the changes, then run

   ```sh
   scripts/prepare_release.py X.Y.Z
   ```

   It checks the version, sets it in `pyproject.toml` (the only place it is
   written), refreshes `uv.lock`, turns the Unreleased section into
   `## [X.Y.Z] - <date>`, and opens a pull request **"Release vX.Y.Z"** on the
   branch `release/vX.Y.Z` (use `--no-git` to only edit the files).
2. Review the PR (CI runs as usual) and **squash-merge** it, keeping the title.
   `tag-release.yml` tags the merge commit `vX.Y.Z` and starts `release.yml`.
3. `release.yml` (see the job graph in the ADR):
   * builds once (wheel, sdist, `SHA256SUMS`, `RELEASE_NOTES.md` from the
     CHANGELOG), runs the whole suite with a real GIMP on **Linux** (pinned
     container), **macOS 15** and **Windows Server 2025** (gimp.org's GIMP 3.2.6,
     `gimp-os-tests.yml`; the built wheel is the one installed), and attests the
     build provenance of the wheel and sdist;
   * creates (or updates, on a re-run) a **draft** GitHub release;
   * waits for your approval of the `testpypi` deployment, publishes there,
     checks the files and drives a real GIMP with the downloaded wheel on Linux,
     macOS and Windows;
   * waits for your approval of the `pypi` deployment, publishes the same files
     (skipped when PyPI already has exactly them), checks them and drives a real
     GIMP with `uv pip install gimp-mcp==X.Y.Z` and `uvx`, on the three OSes;
   * makes the GitHub release public;
   * publishes `server.json` to the official MCP registry (approval of the
     `pypi` environment, GitHub OIDC; see [ADR 0004](adr/0004-discovery-channels.md)).
   A **pre-release** (`scripts/prepare_release.py 1.0.0rc1`, PEP 440 versions `X.Y.ZrcN`, `bN`, `aN`, ordered
   before `X.Y.Z`) goes through the same steps and is published on PyPI (installed only when asked:
   `uvx gimp-mcp==1.0.0rc1`) and as a GitHub **pre-release**, never marked latest; the MCP registry
   keeps listing the last final release.
4. If a job fails, fix the cause and use *Re-run failed jobs*: every step is
   safe to repeat (draft updated, TestPyPI `skip-existing`, PyPI upload skipped
   when identical, a published GitHub release is never modified). Nothing
   reaches PyPI before TestPyPI was verified, and the GitHub release stays a
   draft until PyPI is verified.

### Dry run

*Actions → Release → Run workflow* with **dry_run** checked (any branch),
or `gh workflow run release.yml -f dry_run=true --ref main`: builds, runs the
full suite on Linux, macOS and Windows, uploads the `dist` artifact (to inspect), and stops there — no
attestation, no release, no upload.

## Verifying a release (users)

```sh
# checksums of the downloaded files
sha256sum -c SHA256SUMS --ignore-missing
# provenance: built by this repository's release workflow
gh attestation verify gimp_mcp-X.Y.Z-py3-none-any.whl --repo mhbxyz/gimp-mcp
gh attestation verify gimp_mcp-X.Y.Z.tar.gz --repo mhbxyz/gimp-mcp
```

Files on PyPI also carry PEP 740 attestations (shown on the PyPI file page),
generated by the trusted-publishing upload.

## One-time setup (maintainer)

PyPI uses *trusted publishing*: there is no token to create or store. Do this
once, before the first release:

1. **TestPyPI**: log in at <https://test.pypi.org>, open *Your account →
   Publishing → Add a new pending publisher → GitHub*, and enter exactly:

   | Field | Value |
   |---|---|
   | PyPI Project Name | `gimp-mcp` |
   | Owner | `mhbxyz` |
   | Repository name | `gimp-mcp` |
   | Workflow name | `release.yml` |
   | Environment name | `testpypi` |

2. **PyPI**: same at <https://pypi.org/manage/account/publishing/> with
   environment name `pypi`.
3. The GitHub environments `testpypi` and `pypi` already exist (*Settings →
   Environments*): they require your approval and only accept `v*` tags.

A pending publisher does not reserve the name: until the first upload,
someone else could register `gimp-mcp`. If the first upload fails with
`invalid-publisher`, compare owner, repository, workflow file and environment
on both sides.

Artifacts are checked for secrets and runtime files (tokens, sockets, caches,
`.env`, demo outputs) by `tests/unit/test_distribution.py`.
